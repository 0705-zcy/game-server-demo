# Go 游戏服务端 Demo｜长连接 + 20Hz 状态同步 + 存档

一句话：一个零第三方依赖的 Go 游戏服务端，能登录、能移动、能互相同步、能重启还原，还带一个自写的压测客户端。

做它的目的很明确：对应「游戏服务端开发」这类岗位的硬要求——**在一个不熟悉的语言里，独立跑出一个能演示的服务端闭环**。

---

## 目录结构

```
game-server-demo/
├─ go.mod                 模块声明（无第三方依赖）
├─ main.go                启动入口、参数、优雅关服
├─ protocol.go            上下行消息结构（JSON + 换行分隔）
├─ server.go              连接管理、房间状态、tick 广播、存档落盘
├─ store.go               持久化抽象 + 文件实现（可换成 MySQL/Redis）
├─ cmd/bot/main.go        压测客户端：N 个假玩家并发登录 + 上报位移
├─ tools/manual_client.py 手动试玩脚本（Python，方便现场演示）
└─ players.json           运行时生成的存档（首次启动自动创建）
```

## 协议（TCP + JSON，一行一条）

**客户端 → 服务端**

| type | 字段 | 说明 |
|---|---|---|
| `login` | `playerId`, `name` | 登录，ID 唯一；有旧存档会自动还原 |
| `move` | `x`, `y` | **位移增量**，不是绝对坐标 |
| `chat` | `text` | 群发，最长 200 字 |
| `ping` | — | 心跳 |
| `logout` | — | 主动下线 |

**服务端 → 客户端**

| type | 字段 | 说明 |
|---|---|---|
| `login_ok` | `playerId`, `name`, `restored`, `tick` | `restored` 非空=读到了旧存档 |
| `snapshot` | `tick`, `players[]` | 每 50ms 一条，含全场在线玩家坐标 |
| `chat` | `from`, `text` | 广播聊天 |
| `error` | `msg` | `bad_json` / `not_logged_in` / `already_online` / `server_full` |

## 实测数据（Go 1.23 / Linux，`-race` 构建）

| 项目 | 结果 |
|---|---|
| 100 个并发假玩家，10 秒（Linux，`-race`） | 连接失败 **0**，快照接收 **1996 条/秒**（理论 100×20Hz=2000） |
| 50 个并发假玩家，12 秒（Linux） | 连接失败 **0**，快照 **1000 条/秒** |
| 50 个并发假玩家，6 秒（Windows 本机） | 连接失败 **0**，快照 **882 条/秒**，存档 50 条，重启还原成功 |
| 数据竞争检测（`go build -race` + 100 并发，Linux） | **无告警** |
| 重启还原 | 100 条存档全部读回，重登返回 `restored=true`，坐标一致 |
| 优雅关服（Ctrl+C） | 在线玩家全部落盘，无丢档 |

**没测的**：端到端往返延迟（p99）、单机压到上限（500 是写死的保护值，没压到顶）、跨房间。这三个别在面试里瞎说。

## 五个设计决策（这些才是面试能聊的东西）

1. **读协程 / 写协程 + 有缓冲队列，一个连接一个写协程**
   读只管解包，写独占 `conn`，避免多处并发写同一连接。队列长度 64，满了就踢——**慢客户端不能拖累整个房间**。这是游戏服务端最常被问的一题。

2. **锁内只拷贝，绝不写网络**
   广播是热路径：`RLock` 拷一份状态和连接列表，解锁后才序列化和发送。否则一个卡住的 socket 会把整个锁憋死，全服一起卡。

3. **快照只序列化一次**
   100 人在线时，如果每人一条都快照序列化一次，就是每 tick 100 次序列化，直接爆 CPU。这里序列化一次、发 N 份。

4. **存档先写临时文件再改名**
   防止进程在写一半被 kill 导致存档损坏。Windows 上 `os.Rename` 覆盖已存在文件会失败，所以做了退化处理（先删再改名，牺牲原子性）。

5. **在线表和离线表分开**
   踩过的坑：一开始把启动时读回的存档直接塞进"房间玩家表"，结果老玩家回来登录被判成 `already_online`，永远进不来。分开之后，登录只需从离线表取、移进在线表。

## 已知没做（面试主动讲，别等面试官问）

- **持久化用 JSON 文件，不是 MySQL/Redis**：单文件全量写、无并发隔离，只适合单机 demo。换法已经留好接口：实现 `Store` 的三个方法即可，`server.go` 一行不用改。
- **没有 AOI（兴趣区域裁剪）**：所有人收全场快照，人数上千就崩。真实项目按九宫格/视野裁剪。
- **没有真实鉴权**：`playerId` 直接当身份，没有 token、没有 TLS。生产必须加登录态校验和加密传输。
- **没有断线重连状态机**：客户端断开即出房间，不做短暂保活。
- **协议是 JSON 文本**：可读、好调试，但比二进制协议多占带宽。

## 面试 60 秒口播稿

> 我用 Go 写了一个游戏服务端的最小闭环：TCP 长连接登录、20Hz 全房间快照广播、玩家状态落盘和重启还原。
> 架构上每个连接是读协程加写协程，中间有个长度 64 的发送队列，队列满就踢掉慢客户端，保证不拖累其他玩家。
> 广播是热路径，我在锁里只做状态拷贝，解锁后才序列化，而且整个快照只序列化一次再发 N 份，不然 100 人在线每 tick 就是 100 次序列化。
> 压测是我自己写的 bot 客户端做的：100 个并发连接跑 10 秒，每秒近 2000 条快照，0 连接失败，`-race` 下没有数据竞争。
> 我原来主要写 Python，Go 是这两周现学的——这个项目本身就是我能不能快速换语言的答案。
> 目前持久化还是 JSON 文件，接口留着，换 MySQL 和 Redis 只需要再实现一个 Store。

## 下一步可以加什么（按性价比排）

1. `Store` 换成 MySQL（读写分离）+ Redis（在线状态缓存），这是 JD 里明确要的数据库能力。
2. AOI 裁剪：按坐标分格，只发视野内的人，这是人数上量的前提。
3. 房间/匹配层：把单房间拆成多房间 + 一个匹配服务。
4. 补端到端延迟统计：每条快照带服务器时间戳，客户端算 p99，把"延迟多少 ms"变成一个能报出来的数。
