# Go 游戏服务端 Demo

一个零第三方依赖的 Go 游戏服务端最小实现：TCP 长连接登录、20Hz 全场状态同步、玩家状态原子落盘与重启还原，附带一个自写的压测客户端。

## 目录结构

```
.
├─ go.mod                 模块声明（无第三方依赖）
├─ main.go                启动入口、命令行参数、优雅关服
├─ protocol.go            上下行消息结构（JSON + 换行分隔）
├─ server.go              连接管理、房间状态、tick 广播、存档落盘
├─ store.go               持久化抽象 + 文件实现
├─ cmd/bot/main.go        压测客户端：N 个并发假玩家登录并上报位移
└─ tools/manual_client.py 手动试玩脚本（Python）
```

运行时会在数据目录下生成 `players.json` 存档，首次启动自动创建。

## 环境要求

- Go 1.21 及以上
- 无第三方依赖，不需要联网拉包

## 快速开始

```bash
go run . -addr :9000 -http :9001 -data players.json
```

另开一个终端做压测，100 个并发假玩家跑 15 秒：

```bash
go run ./cmd/bot -addr 127.0.0.1:9000 -n 100 -d 15s
```

查看实时在线人数：

```bash
curl http://127.0.0.1:9001/stats
```

手动试玩：

```bash
python tools/manual_client.py
```

Windows 下另附四个 `.bat` 脚本，分别对应启动服务端、跑压测、查在线人数、手动试玩，双击即可运行，脚本内部会自行编译。

## 协议（TCP + JSON，一行一条）

**客户端 → 服务端**

| type | 字段 | 说明 |
|---|---|---|
| `login` | `playerId`, `name` | 登录，ID 唯一；有旧存档会自动还原 |
| `move` | `x`, `y` | 位移增量，不是绝对坐标 |
| `chat` | `text` | 群发，最长 200 字 |
| `ping` | — | 心跳 |
| `logout` | — | 主动下线 |

**服务端 → 客户端**

| type | 字段 | 说明 |
|---|---|---|
| `login_ok` | `playerId`, `name`, `restored`, `tick` | `restored` 非空表示读到了旧存档 |
| `snapshot` | `tick`, `players[]` | 每 50ms 一条，含全场在线玩家坐标 |
| `chat` | `from`, `text` | 广播聊天 |
| `error` | `msg` | `bad_json` / `not_logged_in` / `already_online` / `server_full` |

## 实测数据

| 项目 | 结果 |
|---|---|
| 100 个并发假玩家，10 秒（Linux，`-race` 构建） | 连接失败 0，快照接收 1996 条/秒（理论上限 100×20Hz = 2000） |
| 50 个并发假玩家，12 秒（Linux） | 连接失败 0，快照 1000 条/秒 |
| 50 个并发假玩家，6 秒（Windows） | 连接失败 0，快照 882 条/秒，存档 50 条，重启还原成功 |
| 数据竞争检测（`go build -race` + 100 并发，Linux） | 无告警 |
| 重启还原 | 100 条存档全部读回，重登返回 `restored=true`，坐标一致 |
| 优雅关服（Ctrl+C） | 在线玩家全部落盘，无丢档 |

尚未测量的指标：端到端往返延迟（p99）、单机连接上限（代码中 `maxSessions=500` 是保护值，未压到顶）、跨房间场景。

## 设计取舍

1. **一条连接一个读协程 + 一个写协程，中间有长度 64 的发送队列**
   读协程只负责解包，写协程独占 `conn`，避免多处并发写同一连接。队列满即剔除该连接，慢客户端不会拖累整个房间。

2. **锁内只拷贝状态，不在锁内写网络**
   广播是热路径：在 `RLock` 内拷贝状态和连接列表，解锁后才序列化与发送。否则一个阻塞的 socket 会长时间持有锁，影响全房间。

3. **快照只序列化一次**
   100 人在线时若逐连接序列化，每 tick 就是 100 次序列化。这里序列化一次，广播 N 份。

4. **存档先写临时文件再改名**
   防止进程在写一半被终止导致存档损坏。Windows 上 `os.Rename` 覆盖已存在文件会失败，因此做了退化处理（先删再改名，牺牲原子性换取可用性）。

5. **在线表与离线表分离**
   早期版本把启动时读回的存档直接放进房间玩家表，导致老玩家重新登录被判为 `already_online`。拆分后，登录只从离线表取数据并移入在线表。

## 已知限制

- **持久化为 JSON 文件，未接 MySQL/Redis**：单文件全量写、无并发隔离，只适合单机 demo。已抽象 `Store` 接口，替换存储实现不需要改动 `server.go`。
- **没有 AOI（兴趣区域裁剪）**：所有玩家接收全场快照，人数上千后不可用。
- **没有真实鉴权**：`playerId` 直接作为身份，无 token、无 TLS，生产环境需要补登录态校验与加密传输。
- **没有断线重连状态机**：客户端断开即出房间，不做短暂保活。
- **协议为 JSON 文本**：可读、易调试，但比二进制协议占用更多带宽。

## Roadmap

1. `Store` 接入 MySQL（持久化）与 Redis（在线状态缓存）
2. AOI 裁剪：按坐标分格，仅下发视野内玩家
3. 房间与匹配层：单房间拆为多房间并引入匹配服务
4. 端到端延迟统计：快照携带服务器时间戳，客户端计算 p99
